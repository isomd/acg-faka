# Dola 购买发码与分批提货

## 使用方式

新版代码中，主站单规格、自动发货、绑定 Dola 货源（type=3）的商品，其**新购买订单**改为交付一个兑换码。购买数量为该码的总额度：买 100 个，获得额度为 100 的一个码；先兑换 10 个，剩余 90 个，下次可继续提取。

付款发码不会调用上游提货接口。客户在首页「兑换码提货」入口（`/user/index/redeem`）提交兑换码和本次数量，才向上游实际提货。单次兑换 1–1000 个，较大额度分批提取。码可在原订单查询/购买记录中查看；请像账号密码一样妥善保管，知道完整码的人可以兑换。

商品继续绑定原 Dola 货源与 `dola-account`，无需重新导入商品或把上游 KEY 交给买家。原售价、阶梯价不变。多规格或预选卡模式不支持购买发兑换码，不能为这类商品开启该路径。

历史订单保存默认直接交付模式，既有已交付账号不会被转换成兑换码。兑换形成的零金额订单同样直接交付账号，不会递归产生新码。非 Dola 商品的付款发货逻辑不变。

## 库存与失败处理

可售额度 = 上游实际剩余库存 − 已售兑换码的未用额度 − 尚未发码购买订单的数量，同一货源下的不同商品共用此额度池。锁定兑换码不代表免除交货义务，因此仍占用额度；旧码/后台生成码也计入占用。

创建新购买订单时通过货源行锁串行校验可售额度；支付后占用由订单转换为兑换码，不会双重扣减。真正兑换时校验上游原始库存，而不是可售额度。因此可售额度为零，不妨碍已购买额度的用户提货。

未支付订单保守占用额度，不自动按时间释放。清理未支付订单前，应先关闭支付平台对应订单，确认无法再支付，再在后台清理；否则迟到的支付通知可能找不到本地订单。人工审核中的已支付未发码订单同样保留占用。

重复支付通知返回原码，不重复生成。提货失败不扣兑换额度；相同 `request_token` 的提货重试返回已完成结果。上游已提货但本地事务回滚时，沿用 Dola 独立提货账本恢复原账号，即使扣货后库存已归零也允许恢复；未知/未完成的上游批次仍由现有 Dola 恢复逻辑核对，不能绕过该逻辑直接扣额度。

不得在有未结清额度时随意切换商品货源。新订单与自动发码保存货源快照，变更货源会拒绝发码/兑换，原占用不会被迁移到新货源。恢复原货源或人工核对后再处理。

本地额度并非上游库存预留。上游网页人工提货、另一个网站使用相同 KEY、后台额外生成兑换码、或不同货源配置重复使用同一 KEY，都可能令实际库存少于已售额度；禁止将这些情形视为已由行锁消除。需管理好 KEY 和人工额度发放。

## 升级与验证

首次访问符合条件的库存/购买入口会增量补充兑换表与订单字段，原字段与数据保留；全新安装使用 `kernel/Install/Install.sql`。数据库需要 CREATE/ALTER 权限，订单、兑换表与货源表必须支持事务及行锁（MySQL InnoDB）。兑换码 HMAC 密钥保存在数据库私密配置中，购买前自动初始化，不通过前台配置接口返回。

部署前先备份数据库与持久数据。本文及本地修改本身不表示已经发布到生产。

回归测试命令（PHP 8.1+，已安装项目依赖，启用 pdo_sqlite 和 mbstring）：

```sh
php tests/RedeemPurchaseTest.php
php tests/MercuryProtocolTest.php
php tests/TradeCaptchaTest.php
node tests/CommodityListStockTest.js
node tests/ItemCaptchaTest.js
```

购买发码测试使用隔离的临时 SQLite 数据库、真实订单处理和兑换控制器，以及上游接口替身，不接触线上配置、订单或实际提货。覆盖发码、分批提货、重复通知、重复提货、库存为零时恢复原批次、失败回滚、审核暂停、货源变化及旧订单兼容。

SQLite 测试不验证 MySQL 并发行锁或真实 Mercury 通知；发布前还需在隔离的 MySQL 测试库验证并发购买、支付通知与兑换竞争，以及通过支付沙箱/测试订单验证真实通知。不要用生产货源做自动化提货测试。
